Written from the ticket's "Done when" only, before the code exists.

## How the integration tests prove it

The tests look at the app the way a person does, so they accept any way of building the screen and any way of reading the feed.

- **"The feed above" is the real feed.** It was saved from `https://xskt.com.vn/rss-feed/mien-nam-xsmn.rss` on 11 November 2026, unchanged. Its five draw days run from 06/11 to 10/11/2026. It holds exactly the ticket's numbers: Bạc Liêu 10/11 with ĐB 267832 and `7: 8078: 82`, and Hồ Chí Minh 09/11 with ĐB 921440 and `7: 0878: 43`. Every other number in it is the site's own.
- **The site's answer comes from the tests.** `results_site.dart` hands every connection the app's HTTP client opens to a small web server inside the test app, whatever address was asked for, so no test reaches the real site. That server answers with the saved feed (unless a test says otherwise), holds the request without answering, or answers with a page that isn't a feed. Everything else is real: the camera, ML Kit's add-on channel answered as in tickets #18 and #24, the screens and the touches.
  - **The one limit:** the app must fetch through Dart's own HttpClient (`dart:io`), as the `http` and `dio` add-ons do by default on Android. A fetch that goes around it, through a phone-side add-on, isn't seen. Every test that expects the feed to be fetched checks that the app asked for `https://xskt.com.vn/rss-feed/mien-nam-xsmn.rss`, by scheme, host and path, so such a fetch fails with a message saying so, instead of passing by reaching the live feed.
- **The feed is fetched for each scan.** The site's answer is set at the start of each test, before the scan, and the no-internet criterion says a scan with no internet shows "Không tải được kết quả, thử lại sau". A feed kept from an earlier scan would show a result instead, so a kept feed fails the tests.
- **"The three fields have been read"**: ML Kit's text has the ticket's number, province and date, in the form ticket #24's rule reads, e.g. `BẠC LIÊU`, `TP. HỒ CHÍ MINH`, `10-11-2026`, `267832`. The read finishes straight after the shutter. The photo isn't checked until the end, so the timing tests start watching at once, even if the app starts fetching at the shutter.
- **"The screen shows ... below them"** means: the words on screen, top to bottom, are exactly ticket #24's three lines (`Số vé: …`, `Tỉnh: …`, `Ngày: …`), then the answer's lines, and nothing else; and the photo still shows whole above them, as on the temporary screen. For a win, the answer is "Chúc mừng! Bạn trúng", then one line per prize. The criteria give no order for 921443's two prizes, so they're accepted in either order, below "Chúc mừng! Bạn trúng". Lines are matched as in ticket #24: texts side by side on one line count as one line, and runs of spaces count as one.
- **A win shows only the prizes won.** 267832 shows only Đặc biệt, as ticket #27's rules say the Đặc biệt ticket doesn't also win may mắn. 123482's only match in Bạc Liêu 10/11 is Tám `82`, the part after `8078: `, so it shows only Giải Tám, and only a read that splits `7: 8078: 82` into Bảy `807` and Tám `82` finds it. 111111 matches nothing.
- **The right day and province.** Hồ Chí Minh is in the feed twice, 09/11 and 07/11, with different numbers, and 921443 wins only against 09/11. Cà Mau is in the feed on 09/11 but not on 10/11, so a check that looked for the province on any day would not show 4d.
- **Just outside the feed's days.** "After the newest draw day" uses 11-11-2026, the day after 10/11, with Cần Thơ, which isn't in the feed at all. "Before the oldest" uses 05-11-2026, the day before 06/11, with An Giang, also not in the feed. Neither may show 4d, because the date decides first.
- **"Screen 4d shows" and "Thử lại opens the camera as it does now"** are ticket #24's own checks: 4d's words and one "Thử lại" button, no photo, then the camera screen with its shutter, Android saying the app is using the camera, still there 3 seconds later.
- **No internet** puts the emulator in airplane mode and checks Android reports no network, then lets the app's request go out for real, so it fails the way it does on a phone with no connection. The test turns airplane mode off again when it ends, even if it fails.
- **"Doesn't answer within 10 seconds":** the site takes the request and never answers. "Không tải được kết quả, thử lại sau" must not show until at least 9 seconds after the app asked, and must show by 12.5 seconds. The slack covers the time between looks and the time an order takes to come back. Then the three lines and that answer must be the only words on screen.
- **"Can't be understood":** the site answers at once, with success, but with a short web page ("Trang đang bảo trì...") instead of the feed, as a site under maintenance might.
- **"Đang đọc vé..." stays until the answer shows:** the site holds the request. Once the read has finished and the app has asked for the feed, the test looks at the screen for 3 seconds: every look must show the line "Đang đọc vé..." and no answer, prize or 4d. It stops sooner if the request has waited 8 seconds, so the app's own 10 seconds never run out. Then the site answers with the saved feed, and the screen must show the three lines and "Chưa trúng lần này", and nothing else, so "Đang đọc vé..." has gone. Whether the three lines already show while loading isn't checked, because no criterion says.
- **No errors:** every test also checks the app raised no error since it began, including the three where loading fails.

**Not tested:**

- A site that answers with an error code, such as 404 or 500. No criterion says which message it gets.
- The draw time, result screens 4a–4c, older results and the retake option, which the ticket leaves out.

## Running the automated tests

Start the emulator with `fvm flutter emulators --launch Pixel_10`. From `app/`:

```sh
export ANDROID_SERIAL=emulator-5554
fvm flutter drive -d "$ANDROID_SERIAL" \
  --driver=integration_test/results_driver.dart \
  --target=integration_test/ticket_text_app.dart
```

The emulator doesn't need the internet: the "no internet" test cuts it on purpose, and every other test gets the saved feed. Don't touch the emulator during a run. If a run stops in the middle of the "no internet" test, check that airplane mode is off afterwards: `adb -s "$ANDROID_SERIAL" shell cmd connectivity airplane-mode disable`. If every test stops in SETUP with the home screen not showing, the emulator is the problem, not the app (backlog item 55): `adb -s emulator-5554 emu kill`, then `fvm flutter emulators --launch Pixel_10 --cold`, and wait a couple of minutes.

The updated older tests, and only those, run by name: `flutter drive` hands `--name` to `dart test`, which runs the tests whose names match. Keep the patterns free of commas, because `flutter drive` splits its arguments at commas.

```sh
fvm flutter drive -d "$ANDROID_SERIAL" \
  --driver=integration_test/ticket_fields_driver.dart \
  --target=integration_test/ticket_text_app.dart \
  --test-arguments=test --test-arguments=--reporter=expanded \
  '--test-arguments=--name=only the answer of ticket #28'

fvm flutter drive -d "$ANDROID_SERIAL" \
  --driver=integration_test/ticket_text_driver.dart \
  --target=integration_test/ticket_text_app.dart \
  --test-arguments=test --test-arguments=--reporter=expanded \
  '--test-arguments=--name=with an answer below them|then the camera opens as normal|Given the person left a photo'

fvm flutter drive -d "$ANDROID_SERIAL" \
  --driver=integration_test/photo_screen_driver.dart \
  --target=integration_test/ticket_text_app.dart \
  --test-arguments=test --test-arguments=--reporter=expanded \
  '--test-arguments=--name=Given a photo was taken earlier|Given the photo screen is open|Given the person left the photo screen|then the home screen shows and no photo screen appears'

fvm flutter drive -d "$ANDROID_SERIAL" \
  --driver=integration_test/photo_crop_driver.dart \
  --target=integration_test/photo_crop_app.dart \
  --test-arguments=test --test-arguments=--reporter=expanded \
  '--test-arguments=--name=with the answer of ticket #28|then the app holds only one photo|when the person taps the shutter and the crop fails|when the person taps the shutter again|when they press back before the temporary screen opens|Given the person left a photo'
```

These tests are not picked up by `fvm flutter test integration_test`, because they run on the Mac.

## Manual steps

Screenshots go in `docs/evidence/28/`.

### Before you start

1. Connect the Pixel 7 and check that `adb devices` lists it as `device`. Put its serial in `ANDROID_SERIAL`: `export ANDROID_SERIAL=<the Pixel 7's serial>`.
2. Check the Pixel 7 has the internet, on Wi-Fi or mobile data.
3. Have a real paper miền Nam ticket whose draw day is one of the last five draw days in the live feed. To see which days those are, open `https://xskt.com.vn/rss-feed/mien-nam-xsmn.rss` in a browser: each item's title gives its day.
4. Install the release build, which is what a person gets, so the step also shows the internet permission is in the app: from `app/`, run `fvm flutter run --release -d "$ANDROID_SERIAL"`, then stop it with `q`.

### Step 1: a real ticket against the live feed, on the Pixel 7

1. Open **Dò Vé Số** on the Pixel 7.
2. Tap **Quét vé**. If Android asks, tap **While using the app**.
3. Lay the ticket flat in good light, fill the dashed frame with it, and tap the shutter.
4. Wait until "Đang đọc vé..." goes away.
5. From the repo root, take the screenshot: `adb -s "$ANDROID_SERIAL" exec-out screencap -p > docs/evidence/28/real-ticket-pixel7.png`.
6. Check the answer against the site: open the day's page on xskt.com.vn for the ticket's province, and work out by hand what the ticket wins with the table in `docs/PRIZES.md`.

**Should happen:**

- The photo shows at the top, with `Số vé: …`, `Tỉnh: …` and `Ngày: …` below it, matching the paper ticket.
- Below them is one of the answers: "Chúc mừng! Bạn trúng" with one line per prize, "Chưa trúng lần này", "Chưa có kết quả" or "Vé quá cũ, không dò được". Or screen 4d, if the province wasn't drawn that day.
- The answer matches what you worked out from the site.
- It must not be "Không tải được kết quả, thử lại sau" while the phone has the internet. That would mean the fetch failed, for example because the release build has no internet permission.
- If the screen shows 4d because the ticket couldn't be read, or wrong fields, that's ticket #24's reading, not this ticket. Retake the photo and note the try in the evidence.

**Screenshot:** `real-ticket-pixel7.png`. Before committing, check the screenshot shows nothing private around the ticket, such as a hand, feet or a room. Crop or black it out if it does.
