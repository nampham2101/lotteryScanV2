# Tests for ticket #18: show the text ML Kit reads under the taken photo

Written from the ticket's "Done when" only, before the code exists.

**Where these run:** all the automated tests run on the `Pixel_10` emulator, because the ticket names no device for them and the emulator can prove them: the tests choose what ML Kit answers, so they don't need a ticket in front of the camera. Its back camera sees a room, and `adb emu rotate` gives a second view of it, so two different photos need nobody holding anything. Manual step 1 runs on the Pixel 7, because the ticket names that phone and only a real camera can look at a real ticket.

## How the integration tests prove it

The tests look at the app the way a person does, so they accept any way of building the screen: any name, any way of drawing the photo, any way of sharing the space between the photo and the text.

- **ML Kit's answers come from the tests,** except in one test. ML Kit gets its work through one message channel of its add-on, and `ticket_text_app.dart` answers on that channel. The camera, the screens, the kept photo and the touches are all real. Only that channel is replaced, so the app can call ML Kit any way it likes. The one limit: the app must call it from the main part of the app, not from a background worker, or the tests can't see the call.
- **The real read.** One test lets real ML Kit read the emulator's real photo, and the channel only writes down what it gave. The read must come back with an answer, or the test fails: a real read that throws is a broken connection, not a photo with nothing to read. The screen must then show exactly that answer, or "Không đọc được vé" if its text is empty, as it can be for a room. This proves the real add-on is connected, which a chosen answer can't. The test doesn't decide what the room reads. Manual step 1 proves it on a real ticket.
- **"Straight away"** means the screen doesn't wait for ML Kit. The test keeps the read unfinished, so the screen can only open before the answer, and the read must still be unfinished at the end. The ticket gives no time limit, so the test uses the usual wait for a screen change, 15 seconds.
- **"The photo on top, whole and not cut off"** means the photo that was just kept is drawn, whole and upright, between the phone's top bar and the first text. The test reads the real file and searches a real screenshot for it at every size from a quarter of the screen's width up. A cropped, stretched or sideways photo isn't found, and neither is a photo under the text or behind the top bar.
- **"Exactly as ML Kit gives it"** compares all the words on screen, top to bottom, with the chosen text, letter by letter. That text has accents, a repeated line, two spaces in a row and an order no sorting would give. Anything added, removed or tidied up fails, and so does any other word on screen.
- **ML Kit's `text` value, not its pieces:** ML Kit also gives its text in blocks. The chosen answers list the blocks in the opposite order, so text put together from them comes out in the wrong order.
- **The right photo was read.** The tests compare the picture ML Kit was given with the kept file, by a checksum of the file's contents. Reading an older photo fails.
- **"Scrolls to its last line"** chooses a text of 150 lines, then swipes on it with real touches until it stops moving. The accessibility tree must show a part of the screen that scrolls, and it must reach the end of its scrolling, which is what puts the last line in view. The last line must also be in the app's list of what's on screen, but that list holds a text in one piece whether it's scrolled or not, so the end of the scrolling is the real proof. If nothing scrolls, the test fails.
- **"The photo stays in place"** notes where the photo is before the first swipe, and compares a screenshot with the photo at that same place after the last one.
- **"With no error"** counts every error the app raises, of either kind Flutter can report, from the start of the test. Leaving tests also finish or fail the read after the person left, because that's when a screen that's gone would cause an error, and the home screen must still be there three seconds later.
- **"As normal"** taps the real button, and the camera screen must open with its shutter, with Android saying the app is using the camera.
- **"Only the new photo and its own text"** takes two photos of different views, by turning the emulator's camera. It covers all the ways the earlier read can end: finished before the person left, finishing while the new photo is being read, finishing after the new text shows, and failing while the new photo is being read. An earlier answer must never reach the screen, and the screen must keep showing "Đang đọc vé..." until the new photo's own answer. These tests expect the app to ask ML Kit for the new read while the earlier one is unfinished, as ML Kit allows.

## Changes to ticket #10's tests

The ticket says these change on purpose, because they expect a photo screen with no text.

- `Given the photo screen is open, then it has no text and no buttons` in `app/integration_test/photo_screen_driver.dart` is now `... then it has no buttons`. The ticket's "Not included" keeps it free of buttons.
- **"The photo screen"** used to mean no words and no buttons. In `helpers/photo_screen.dart` it now means words, no buttons, and neither the home screen nor the camera screen.
- **"The whole photo"** used to mean as large as the screen allows. In `helpers/shown_photo.dart` it now means whole, at any size, above the first text. Ticket #18 replaces the screen's layout, so `differenceFromScreen` is replaced by `findPhoto`.
- **`givenPhotoScreenOpen`** now waits for the read to finish, so the pinch and double-tap tests compare a screen that doesn't change by itself. `givenPhotoTaken` is the same without that wait.

`docs/tests/10.md` still describes the old screen, because this ticket's tests can't change that file.

`camera_app.dart`, `helpers/driven_app.dart` and `helpers/app_screen.dart` haven't changed. `helpers/phone.dart` gained one new method, `swipeUp`, and nothing already there changed, so the tests of tickets #5, #8 and #9 aren't affected by test changes.

## Running the automated tests

Start the emulator with `fvm flutter emulators --launch Pixel_10`. From `app/`:

```sh
export ANDROID_SERIAL=emulator-5554
fvm flutter drive -d "$ANDROID_SERIAL" \
  --driver=integration_test/ticket_text_driver.dart \
  --target=integration_test/ticket_text_app.dart

fvm flutter drive -d "$ANDROID_SERIAL" \
  --driver=integration_test/photo_screen_driver.dart \
  --target=integration_test/camera_app.dart
```

The first command is this ticket's tests, the second is ticket #10's changed tests. Don't touch the emulator during a run. If a run is stopped by force in the middle of a "new photo" test, the emulator's camera stays turned. To put it back, run `adb -s emulator-5554 emu rotate` until the camera screen shows the room upright, with the TV standing on its cabinet.

If every test stops in SETUP with the home screen not showing, the emulator is the problem, not the app. A stuck notification shade and Android's "isn't responding" pop-up both did this during the first run (backlog item 55). What cleared it: `adb -s emulator-5554 emu kill`, then `fvm flutter emulators --launch Pixel_10 --cold`, then waiting a couple of minutes for the load to drop before starting the tests.

These tests are not picked up by `fvm flutter test integration_test`, because only the Mac can read the kept photo and turn the emulator's camera.

## Manual steps

Screenshots go in `docs/evidence/18/`.

### Before you start

1. Connect the Pixel 7 and check that `adb devices` lists it as `device`.
2. Put its serial in `ANDROID_SERIAL`: `export ANDROID_SERIAL=<serial from adb devices>`. Don't write it in any file.
3. Install the app: from `app/`, run `fvm flutter run -d "$ANDROID_SERIAL"`, then stop it with `q`.
4. Have a real lottery ticket ready, on a flat surface with good light. The screenshot goes in this public repository, so use a ticket you're happy to show.

### Step 1: a real ticket on the Pixel 7

1. Open **Dò Vé Số** on the Pixel 7.
2. Tap **Quét vé**. If Android asks, tap **While using the app**.
3. Hold the phone over the ticket so the ticket fills the dashed frame and its print looks sharp.
4. Tap the shutter, and keep watching the screen.
5. Wait until "Đang đọc vé..." goes away.
6. From the repo root, take the screenshot: `adb -s "$ANDROID_SERIAL" exec-out screencap -p > docs/evidence/18/real-ticket-pixel7.png`.

**Should happen:**

- The photo of the ticket shows on top, whole and not cut off, as soon as the shutter is tapped, with "Đang đọc vé..." below it.
- "Đang đọc vé..." goes away, and words from the ticket show below the photo. They should include words you can find on the ticket, such as "XỔ SỐ KIẾN THIẾT". ML Kit may misread some of them: this step proves words from the ticket reach the screen, not that every word is right.
- "Không đọc được vé" must not show. If it does, try again with better light before calling it a failure, and note the try in the evidence.

**Screenshot:** `real-ticket-pixel7.png`.
