# Tests for ticket #24: read the ticket number, province and date from ML Kit's text

Written from the ticket's "Done when" only, before the code exists.

**Where these run:** everything runs on the `Pixel_10` emulator, the automated tests and manual step 1. The ticket names no device, and the emulator can prove every item: the tests choose ML Kit's text, so no ticket has to be in front of the camera, and 4d's look only needs a photo that doesn't read as a ticket, which the emulator's room gives. The "Camera won't start" tests also stay on the emulator: they make the camera refuse or fail on purpose through the camera add-on, which works the same on any device, and a real phone wouldn't make it more real, because Android closes the app when camera access is taken back, so a real refusal can't reach a 4d that's already open on any device. No item needs the Pixel 7.

## How the integration tests prove it

The tests look at the app the way a person does, so they accept any way of building the screens and any way of writing the rule.

- **ML Kit's text comes from the tests.** As in ticket #18, `ticket_text_app.dart` answers on ML Kit's add-on channel, and everything else is real: the camera, the screens, the kept photo and the touches. Its answer lists the blocks in the opposite order to the text, so a rule that searched the blocks would find the wrong "first" number, province or date.
- **Each test's text has the two other fields valid**, so a test fails only on the field it's about. For example, the `D051 669` text also has `CẦN THƠ` and `04-11-2026`.
- **"Exactly three lines, in this order, and none of ML Kit's text"** reads every word on screen, top to bottom, and compares the lines with the three expected ones. Texts drawn side by side on one line, such as `Số vé:` and `871723` drawn apart, count as one line, and runs of spaces count as one. Anything else written on screen fails. The photo must be found whole and upright above the first line, as in ticket #18. ML Kit's text includes a line the rule must skip, `LOẠI VÉ 10.000Đ`.
- **"The screen shows `Số vé: …`"** in the single-field tests looks for the one line that starts with `Số vé:`, `Tỉnh:` or `Ngày:` and compares it whole. These tests don't check the other two lines.
- **"4d shows"** means: its words, top to bottom, are exactly "Không đọc được vé", "Chụp lại ở nơi đủ sáng, giữ vé phẳng và rõ nét." and "Thử lại", with a line break allowed in place of a space; "Thử lại" is the screen's only button; and the photo isn't anywhere on screen. A name for screen readers on the icon above the title isn't counted. Because 4d has no photo, the temporary screen's old "Không đọc được vé" line under the photo doesn't pass as 4d.
- **"The camera screen opens"** after "Thử lại" or back means the camera screen with its hint and its one shutter, Android saying the app is using the camera, and the same screen still there three seconds later.
- **"As it does today"** repeats ticket #18's check: the read is kept unfinished, the screen opens with the photo whole above "Đang đọc vé...", and nothing else written. This test is expected to pass before the feature exists.
- **No errors:** the tests that end on a result also check the app raised no error since the test began.

### Camera won't start

- **The camera refuses or fails because the tests say so.** `camera_start_app.dart` is `ticket_text_app.dart` plus answers on the camera add-on's own messages for starting the camera, the same way ticket #22's tests spoil a picture on the add-on's message for taking one. Everything else is real. A test first brings up 4d the normal way, with the camera working, and only then makes every later camera start go wrong, until the next test begins.
  - **Refused:** the add-on answers that access is refused, with the code Android's refusal gives, `CameraAccessDenied`. Android isn't asked to refuse, because it closes the app when access is taken back, so a real refusal can never reach a 4d that's already open. A real refusal is always the camera's first start since the app opened. Here the add-on still holds the preview of the camera that took the photo, and letting it go a second time fails inside the add-on, so while refusing the fake answers that for the add-on, as a real refusal finds no earlier preview.
  - **Fails for another reason:** access is allowed, but the camera won't start, with the error CameraX gives when it can't find a camera to use.
  - The one limit: the app must start the camera through the camera add-on, as it does today. A failing test's message says how many camera starts the test refused or failed, so a test that never reached its "Given" is easy to spot.
- **"The home screen shows with the 'Cần dùng camera' pop-up"** means: the pop-up appears, with ticket #9's words and its one "Đóng" button, and tapping "Đóng" leaves the home screen. The pop-up hides what's behind it from the tests, so closing it is how they see it was on the home screen and not on 4d or the camera screen.
- **"The home screen shows with the note 'Lỗi camera, thử lại'"** means: the note's words show while the home screen is showing, and no pop-up. From the moment the note first shows until it's gone, the home screen stays, and it's still there 3 seconds after the note goes. Screens on the way from 4d to home aren't checked.
- **"Fades after about 3 seconds"** means: the note is seen for at least 2 seconds, and is gone within 4.5 seconds of first showing. Watching takes a moment between looks, so a note shown for 3 seconds is seen for a little less, and the upper limit leaves room for it sliding in and out. Where on screen the note shows isn't checked, because no criterion says.
- **"The home screen stays"** after "Quét vé" means: every look from the tap until the note is gone shows the home screen, or nothing for a moment while the screen is redrawn. The camera screen never shows, not even briefly.
- These tests don't check for app errors, because a camera that won't start can make the camera add-on itself report one.

**Not tested:** the first province "found in the text" could mean the first by place in the text or the first in the list of 21. `CẢN THƠ` before `VINH LONG` gives Cần Thơ either way, so the test accepts both. No criterion tells them apart.

## Changes to the tests of tickets #10, #18 and #22

Ticket #24 shows three lines "in place of ML Kit's text", and 4d where the temporary screen used to show "Không đọc được vé". These older tests expected the old screen, so they change on purpose:

- **Ticket #18** (`ticket_text_driver.dart`):
  - Removed, because #24 replaces what they check: "ML Kit's text value shows below the photo, exactly as ML Kit gives it", the long text that scrolls to its last line, and both "Không đọc được vé shows below the photo" tests. The new rule, 4d and its look are covered above.
  - The real ML Kit test now expects the three lines below the photo or 4d, and 4d if the text is empty. It doesn't decide what the emulator's room reads.
  - The tests that finish a read and expect its text now give texts with all three fields and expect the three lines.
- **Ticket #22** (`photo_crop_driver.dart`, `helpers/photo_crop.dart`): the reads give texts with all three fields and expect the three lines. The test "the text it read from the cropped photo shows below it, exactly as ML Kit gives it" is renamed to "what it read from the cropped photo shows below it, as the three lines of ticket #24".
- **Ticket #10** (`photo_screen_driver.dart`, `helpers/photo_screen.dart`): these tests let real ML Kit read the emulator's room, which would now open 4d with no photo. They now run on `ticket_text_app.dart` with the reads held, and "the photo screen is open" means the read finished with a full ticket text and the three lines show. What they check about the photo screen is unchanged.
- **New shared helper:** `helpers/ticket_fields.dart`. `helpers/photo_screen.dart` imports it.

`docs/tests/10.md`, `docs/tests/18.md` and `docs/tests/22.md` still describe the old screen and the old commands, because this ticket's tests can't change those files. The command for ticket #10's tests is now the one below.

Ticket #8's camera tests use `camera_app.dart` with real ML Kit, but none of them waits for a read or checks the screen after one, so they're unchanged.

## Running the automated tests

Start the emulator with `fvm flutter emulators --launch Pixel_10`. From `app/`:

```sh
export ANDROID_SERIAL=emulator-5554
fvm flutter drive -d "$ANDROID_SERIAL" \
  --driver=integration_test/ticket_fields_driver.dart \
  --target=integration_test/ticket_text_app.dart

fvm flutter drive -d "$ANDROID_SERIAL" \
  --driver=integration_test/camera_start_driver.dart \
  --target=integration_test/camera_start_app.dart
```

The changed tests of tickets #10, #18 and #22:

```sh
fvm flutter drive -d "$ANDROID_SERIAL" \
  --driver=integration_test/photo_screen_driver.dart \
  --target=integration_test/ticket_text_app.dart

fvm flutter drive -d "$ANDROID_SERIAL" \
  --driver=integration_test/ticket_text_driver.dart \
  --target=integration_test/ticket_text_app.dart

fvm flutter drive -d "$ANDROID_SERIAL" \
  --driver=integration_test/photo_crop_driver.dart \
  --target=integration_test/photo_crop_app.dart
```

Don't touch the emulator during a run. If every test stops in SETUP with the home screen not showing, the emulator is the problem, not the app (backlog item 55). What cleared it before: `adb -s emulator-5554 emu kill`, then `fvm flutter emulators --launch Pixel_10 --cold`, then waiting a couple of minutes before starting the tests.

These tests are not picked up by `fvm flutter test integration_test`, because only the Mac can read the kept photo and compare it with the screen.

## Manual steps

Screenshots go in `docs/evidence/24/`.

### Before you start

1. Start the emulator: `fvm flutter emulators --launch Pixel_10`, and wait until its home screen shows.
2. `export ANDROID_SERIAL=emulator-5554`
3. Install and start the app: from `app/`, run `fvm flutter run -d "$ANDROID_SERIAL"`, then stop it with `q`. This is the plain app, with real ML Kit.

### Step 1: screen 4d next to sketch 4d

1. Open **Dò Vé Số** on the emulator.
2. Tap **Quét vé**. If Android asks, tap **While using the app**.
3. The camera shows the emulator's room, which has no ticket in it. Tap the shutter.
4. Wait until "Đang đọc vé..." goes away and screen 4d shows.
5. From the repo root, take the screenshot: `adb -s "$ANDROID_SERIAL" exec-out screencap -p > docs/evidence/24/4d-pixel10.png`.
6. Open `docs/design/screens.png` and compare the screenshot with sketch **4d. Can't read**.

**Should happen:**

- 4d fills the whole screen, with a white background like the sketch. No photo shows anywhere, not even small or behind the words.
- Top to bottom, in the middle of the screen: a red round icon with an exclamation mark, "Không đọc được vé" in large bold dark text, "Chụp lại ở nơi đủ sáng, giữ vé phẳng và rõ nét." in smaller grey text, centred, and a blue "Thử lại" button with white bold text and rounded corners.
- Nothing else is on the screen: no text from the room, no other button.
- If the screen shows three lines below the photo instead, the room happened to read as a ticket. Point the camera at a different part of the room with `adb -s "$ANDROID_SERIAL" emu rotate`, try again, and note the try in the evidence. Afterwards, run `emu rotate` again until the camera shows the room upright, with the TV standing on its cabinet, so the automated tests find the camera as they expect.
